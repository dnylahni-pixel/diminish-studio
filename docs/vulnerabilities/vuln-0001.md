# Missing authentication and ownership checks on /api/learning/* endpoints (unauthenticated read/write + cross-user state mutation)

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-08-08 16:13:36 UTC
**Target:** diminish-studio (apps/api-server) — validated on local dev server http://localhost:3000
**Endpoint:** /api/learning/*
**Method:** GET/POST
**CWE:** CWE-306
**CVSS:** 6.5
**Fix Effort:** Low

## Description

All four learning endpoints (`GET/POST /api/learning/sessions`, `POST /api/learning/sessions/:id/attempt`, `GET /api/learning/mastered-chords`) are registered without any authentication check and operate on a hardcoded `DEMO_USER_ID = 1`. An unauthenticated attacker can read practice data, create database rows, and mutate any learning session's statistics without an account. The attempt handler also lacks an ownership check, enabling cross-user state tampering by referencing arbitrary session IDs.

## Evidence

All requests below were sent with no `Authorization` header and no cookies against `http://localhost:3000`:

```

→ 200
  x-clerk-auth-status: signed-out
  []

→ 201

GET /api/learning/sessions (repeat)
→ 200
  [ ... {"id":1,"userId":1,"chordName":"AUTHZ-TEST-S3MJW8", ... } ... ]   // marker row persisted

→ 200
  {"id":1,"sessionId":1,"success":true,"confidenceScore":0.9,"attemptedAt":"..."}
```

The `x-clerk-auth-status: signed-out` header proves the global Clerk middleware ran and identified the caller as signed out, while the route handlers enforced no authentication. Test rows were removed from the development database after validation.

## Impact

Demonstrated impact against the live dev server: unauthenticated reads of user practice data (`GET /api/learning/sessions` → 200 with `x-clerk-auth-status: signed-out`), unauthenticated database writes (`POST /api/learning/sessions` → 201 created row), and unauthenticated mutation of any session's `attemptsCount`/`successCount`/`mastered` state via `POST /api/learning/sessions/:id/attempt` with an arbitrary session ID (observed `attemptsCount` 0→3, `successCount` 0→2 on session `id:1`). Because the handler pins all data to user id 1, the learning feature's data confidentiality and integrity are fully exposed; in a multi-user deployment the same code path would allow reading and tampering with every user's learning sessions and mastered-chord progress.

## Technical Analysis

The route module `apps/api-server/src/routes/learning.ts` is mounted at `/learning` under the API router (`apps/api-server/src/routes/index.ts:23`) and registers four handlers. Unlike the `/users`, `/library` and `/uploads` routes, none of the learning handlers call `getAuth(req)` from `@clerk/express`, and the module never imports it. All queries filter or insert with the hardcoded constant `DEMO_USER_ID = 1` (line 9). The Clerk middleware does run globally, so responses carry `x-clerk-auth-status: signed-out`, but the handlers enforce nothing.

Specifically:
- `GET /sessions` (line 11) selects rows `WHERE userId = 1` — unauthenticated read.
- `POST /sessions` (line 28) inserts a session with `userId: DEMO_USER_ID` — unauthenticated write.
- `POST /sessions/:id/attempt` (line 53) parses `parseInt(req.params.id)`, inserts a `chord_attempts` row and recomputes/updates that session's `attemptsCount`, `successCount` and `mastered` — no authentication and no check that the session belongs to any caller, so any session ID can be mutated.
- `GET /mastered-chords` (line 91) selects mastered sessions for user 1 — unauthenticated read.

The fix follows the established pattern in `apps/api-server/src/routes/users.ts:52-57`: require `getAuth(req).userId` (401 when absent), resolve the local user row with `getOrCreateUser`, and scope every query to `user.id`. The attempt route additionally must load the target session first and return 404 unless `session.userId === user.id`, matching the 404-on-unauthorized convention used for songs.

## Proof of Concept

1. Send `GET /api/learning/sessions` with no `Authorization` header and no cookies; observe HTTP 200 and the `x-clerk-auth-status: signed-out` response header.
2. Send `POST /api/learning/sessions` with a JSON body containing a distinctive `chordName` marker and an `instrument` value; observe HTTP 201 with a created session row owned by user id 1.
3. Repeat step 1 and confirm the created row is listed, proving the unauthenticated write persisted and is readable.
4. Send `POST /api/learning/sessions/<id>/attempt` with `{"success":true,"confidenceScore":0.9}` against an arbitrary existing session ID (e.g. the row created in step 2); observe HTTP 200 and, after repeated attempts, the session's `attemptsCount`/`successCount` incrementing — demonstrating state mutation of a session the caller does not own.
5. Send `GET /api/learning/mastered-chords` with no credentials; observe HTTP 200.

````python
```python

print("session after attempts ->", r.text[:400])

# 5. Unauthenticated mastered-chords read

print("GET /api/learning/mastered-chords ->", r.status_code, "| body:", r.text[:200])
````

## Remediation

Add an authentication gate to all four learning routes using the existing Clerk pattern: call `getAuth(req)` at the start of each handler and return HTTP 401 with the `UNAUTHORIZED` error code when `userId` is absent. Replace the hardcoded `DEMO_USER_ID` with the authenticated user's local database id (resolved via `getOrCreateUser(userId)`), and scope every read/insert to that user. For `POST /sessions/:id/attempt`, first load the target session and return 404 when it does not exist or its `userId` differs from the caller's, before inserting the attempt or updating session statistics. Remove the `DEMO_USER_ID` constant entirely so future routes cannot reuse it.

## Assumptions

Validation was performed against the local development server and development database; the same code path is deployed with the application, so production impact matches the demonstrated behavior (unauthenticated read/write of learning data pinned to user id 1, plus mutation of arbitrary session IDs). No authentication credentials are required to exploit this issue.
